# Shroom SDK 产品评审与补充建议

评审日期：2026-10-19。评审对象：[Shroom 当前系统结构](./Shroom-当前系统结构.md)，SDK 版本 0.1.0。

当前结构已经覆盖设备接入、实时展示、服务端录制和按记录 ID 下载。最需要补充的是产品交付标准：用户应该选择哪条路径，数据到底代表什么，遇到异常后能否知道记录是否完整，以及升级后能否解释历史数据。

以下以原结构文档为现状依据。“未说明”表示需要核实，不能据此判定实现缺失；“建议”表示拟补充的产品约定，不代表当前已支持。原结构快照保留不变。

## 最值得反驳的七个判断

### 一 现有产品与新设备的分类不足以确定用户入口

**依据：** 组织原则是“现有产品走快速接入，新设备走基础自定义”。

**质疑：** 同样使用手套，有人只想采一份实验数据，有人要把数据接入自己的应用，有人才需要改协议。仅按设备是否已有封装来分流，还无法回答用户首先该下载什么、运行什么、何时算完成。

**建议：** 在现有设备分类前补上任务选择：采集数据、集成应用、适配新设备。首版优先服务哪类人，应由现有客户任务验证。可以暂以“使用已支持硬件的应用集成开发者”为主用户假设，但不能把它写成已验证结论。

**验收：** 首次用户能够根据自己的任务选对入口，并知道所需硬件、环境、预期结果和当前限制。

### 二 七步完整示例不应自动变成所有任务的必经步骤

**依据：** 快速链路包含 Node.js 取数、WS、前端渲染、录制和下载；同时存在 `device.onData()` 与浏览器直连串口测试台。

**质疑：** 只需要第一帧结构化数据的开发者，为什么必须先理解绘图、录制和下载？只需要实验文件的人，为什么首先面对前后端架构？完整示例值得保留，但每项任务应有自己的完成点。

**建议：** 增加三个最小任务：“读到第一帧”“在自己的应用中消费数据”“获得一份可解释的采集文件”。为浏览器直连、独立快速服务、既有后端客户端提供选择条件。

**验收：** 每条路径都有独立的起点、运行命令、成功结果和下一步，不要求用户先读完全部系统结构。

### 三 多语言下载不能让用户误判为能力对等

**依据：** 首页提供 Python 和 Node.js 下载；完整快速链路当前支持 Node.js 与浏览器，Python 仅有基础串口与矩阵能力。

**质疑：** 用户在下载前是否就知道 Python 无产品级快速服务接口？如果到开发中途才发现，损失的是接入时间与信任。是否补齐 Python，应取决于目标用户任务，而不是语言数量。

**建议：** 下载入口前展示能力矩阵，分别说明产品封装、原始串口、录制、导出、渲染和平台验证范围。将“未支持”“部分支持”“未验证”分开。

**验收：** 用户能在下载前判断所选语言是否支持自己的完整任务；示例和文档与同一发行包对应。

### 四 能画出热力图还不足以证明数据可解释

**依据：** 手套有 256 个原始通道、新分区数据和旧 195 点展示矩阵；顶层统计仍按旧矩阵，不能等同新分区整体统计。当前值为 ADC 或相对归一化值，不直接提供 kPa 或牛顿。

**质疑：** 用户看到一个平均值时，知道它覆盖哪些点吗？新旧统计是否会被误当成同一口径？同一颜色在不同参数下是否代表相同数值？这些会影响分析结论，优先级高于展示形式。

**建议：** 补齐通道映射表、统计范围、归一化公式和参数、无效值规则及版本。兼容字段要明确标注覆盖范围；未经物理标定的数据继续使用 ADC 或相对响应含义。

**验收：** 用单通道非零样本逐项核对映射；原始通道中的有效、保留、未使用和重复映射情况可查；同一原始帧和相同参数产生一致结果。不要求所有 256 通道都必须参与展示。

### 五 采集起停按钮不能替代完整的采集状态约定

**依据：** 关闭网页不等于停止录制；重连可查询服务端状态；停止需等待文件写完；异常中断保留状态。

**质疑：** 开始请求超时后能否重试？设备断开、磁盘写满、服务进程退出分别得到什么状态？用户如何判断“已经停止”和“文件已经完整保存”？这些行为文档尚未给出完整约定。

**建议：** 定义开始中、录制中、停止中、完成、中断和失败状态，写清状态转换、错误原因及恢复动作。网页重连后主动显示仍在运行的会话；开始和停止的重复请求应有明确处理规则。

**验收：** 请求重试不会意外创建重复记录；停止成功与文件完成写入一致；中断会话不能被显示为正常完成；可恢复的完整帧和不可恢复的尾部有明确说明。

### 六 按 ID 下载只解决了文件选择的一部分问题

**依据：** 已有记录 ID、人工标签、状态、帧数、真实或模拟来源和异常信息，支持 CSV 与 JSONL；未内置回放，一次会话一个标签。

**质疑：** 一个月后换一位开发者，能否仅凭文件确定设备、左右手、映射版本和归一化参数？整段“抓握”标签是否混入准备和放松阶段？`frameCount` 只能说明保存了多少帧，不能单独证明采集完整。

**建议：** 先补录制元数据、质量摘要和字段字典，再按场景决定是否做时间段标注与图形回放。会话标签默认表示整段记录的人工描述，不能自动当作逐帧动作真值。

**验收：** 文件交给另一位开发者后，仍能解释每列含义并重建相同分区结果；CSV 与 JSONL 的帧及原始值可对应；模拟来源在文件脱离网页后依然可识别。

### 七 模块齐全不等于交付边界明确

**依据：** 文档同时涉及 SDK、三个桌面平台的上位机下载、快速数据服务、既有后端客户端、AI 问答和 SDK Skill。快速服务与既有后端不是同一协议；当前 ZIP 交付，未发布公共 npm 或 PyPI 包。

**质疑：** 上位机与 SDK 各自服务谁、承担什么任务？哪个进程持有串口和录制状态？用户如何判断 ZIP、浏览器包、服务和文档是否兼容？这些比新增一个下载按钮更影响实际交付。

**建议：** 补齐组件职责、组合方式、发行包清单、支持环境、版本兼容和升级说明。上位机现有能力需单独核实；AI 问答应能标识回答所对应的文档和 SDK 版本。

**验收：** 用户能按任务选对组件；支持的组件组合与版本可查询；不兼容时给出可操作的提示；历史记录仍有对应的数据解释。

## 建议补充到系统结构中的产品约定

以下内容可作为原文后续增加的产品章节。涉及新增接口、字段和状态的名称均为草案，不能直接作为现有 API 文档使用。

### 产品定位与任务范围

- 定位草案：为已支持的触觉硬件提供结构化数据接入、相对触觉响应展示及本地数据采集能力。
- 主用户假设：将手套或手垫接入自有应用的开发者。
- 需要验证的另一类用户：以实验采集和 Python 分析为主的研究人员。如果这类需求占主导，应重新调整 Python、数据元信息与标注的优先级。
- 核心交付结果：用户能选对接入方式，并独立完成所选任务：读取可解释数据、集成应用，或生成可追溯的采集记录。
- 持续保留的边界：未完成标定时不承诺物理压力值；人工标签不代表动作识别结果；三维渲染与多设备同步按场景验证后规划。

### 接入路径与组件职责

| 用户任务 | 当前可参考的路径 | 需要补充的说明 |
| --- | --- | --- |
| 快速确认真实设备是否出数 | 支持产品的 Node.js 连接与 `onData()`；浏览器直连测试台 | 两条路径各自适用环境、支持产品与诊断方法 |
| 将数据接入自己的应用 | Node.js 产品数据；需要浏览器分发时使用快速服务 | 第一帧字段解释、订阅释放及服务退出行为 |
| 实时查看并采集文件 | Node.js 快速服务与示例网页 | 状态、质量提示、文件位置及恢复操作 |
| 连接已经运行的主项目后端 | `BackendSdkClient` | 服务前提与协议差异；不把它当成快速服务客户端 |
| 适配新设备或协议 | 基础串口、拆帧、映射能力 | 适配完成标准、最小样本和自查清单 |
| 无代码完成设备操作或采集 | 上位机能力待核实 | 核实后再决定是否承诺这条路径 |

组件职责建议明确为：设备连接负责串口和解析，快速服务负责分发与录制状态，浏览器负责展示和控制；上位机与这些组件的复用及互斥关系需要另行补充。尤其要说明多个程序访问同一串口时的预期行为。

### 当前能力矩阵

| 能力 | Node.js | 浏览器 | Python |
| --- | --- | --- | --- |
| 已核实产品协议与命名分区 | 支持 | 产品层支持，具体接入路径需查对应示例 | 无产品级快速服务接口，产品封装覆盖待核实 |
| 基础串口 | 支持 | Web Serial，运行环境验证范围待补 | 支持 |
| 快速服务端 | 支持 `serveDevice()` | 通过 `connectStream()` 作为客户端 | 当前无对应产品级接口 |
| 录制与按 ID 导出 | Node.js 本地持久化 | 通过快速服务控制及下载 | 文档未定义对应能力 |
| 展示 | 终端热力图 | 产品视图及通用矩阵 | 文字与绘图示例 |

另外补一张经测试的环境表，写明操作系统、运行时、浏览器、产品型号和固件组合。网站上有对应平台的上位机下载，不能据此推导 SDK 在所有平台完成了同等验证。

### 数据含义与记录元数据

产品数据字典至少覆盖：通道索引、部位、左右手、矩阵坐标、单位、无效点、统计范围和归一化方式。IMU 当前只保留原始字节，应明确字段边界，避免让用户误认为已经获得姿态数据。

建议每条录制关联一份机器可读的记录说明，以下是信息类别，不代表现有字段名：

| 信息类别 | 建议保存内容 |
| --- | --- |
| 记录与来源 | 记录 ID、人工标签、真实或模拟来源、起止时间、最终状态与错误原因 |
| 设备 | 产品型号、左右手、通道数、可获得的设备及固件标识；无法获得时明确记为未知 |
| 解释版本 | SDK、传输协议、产品数据格式、映射及录制格式版本 |
| 数据处理 | 归一化算法与参数、基线及校准信息；未使用校准时明确记录 |
| 时间 | 主机接收时间含义及单位、会话内帧序号；设备时间戳或源序号仅在协议提供时记录 |
| 质量与文件 | 已接收、解析成功、已保存帧数，能观测到的错误与队列溢出，导出文件校验信息 |

设备协议未提供足以核对源帧的序号或等价信息时，不能仅凭主机接收和保存数量计算真实源端丢帧率。质量报告应区分“可观测到的异常”和“当前无法判断的数据损失”。

CSV 还需定义列顺序、单位、缺失值、字符编码和标签转义；明确一行表示一帧还是一个采样点。JSONL 所称“原始记录”也应说明是解码后的原始 ADC 还是串口字节，避免用户误以为可用它重新验证所有协议解析行为。

### 采集状态与故障行为

| 场景 | 建议的产品行为 |
| --- | --- |
| 开始录制 | 返回唯一记录 ID；同一开始请求重试有去重规则；无数据时的状态和提示明确 |
| 浏览器关闭或断网 | 延续已说明的服务端录制行为；重连时主动恢复状态并提供停止入口 |
| 设备断开 | 显示数据中断及原因；若支持重连续录，保留中断区间；否则结束为中断状态 |
| 停止录制 | 明确最后一帧的接收边界；文件完成写入后才报告完成；重复停止返回一致结果 |
| 服务正常退出 | 明确活动会话如何结束及串口、服务、文件的关闭顺序 |
| 进程异常退出 | 重启后区分完整记录和中断记录；说明可恢复范围及尾部损失情况 |
| 磁盘写入失败 | 及时显示失败原因和已保存帧数；不能继续显示为正常采集 |
| 多个网页同时控制 | 定义是否允许并发录制、由谁停止及如何防止误操作 |
| 空记录或未完成记录下载 | 明确允许下载的状态、错误提示及文件中的中断标识 |

建议状态为“开始中 → 录制中 → 停止中 → 完成”，并允许明确转入“中断”或“失败”。这些属于拟补充的契约，应先对照现有实现核实。

### 版本交付与支持

- 每个 ZIP 附带版本、内容清单、依赖安装方式、对应文档及可运行示例。离线安装是否支持需单独说明。
- 发布经验证的硬件和环境组合，以及浏览器客户端与快速服务的兼容关系。
- 分开说明传输协议能否解码、字段语义是否兼容、映射是否变化和旧记录如何解释。
- 保留旧 195 点字段时，给出适用范围、替代字段和迁移示例；废弃周期按实际支持能力确定。
- 明确日志和诊断信息的导出入口、已知问题与反馈渠道。对外承诺响应时间前先确认团队承接能力。
- 本机试用沿用当前访问边界；若正式承诺跨机协作，再将认证、授权与传输保护纳入该模式的交付标准。

## 发布失败预演与优先级

假设下一次对外试用后，用户反馈“能看到图，但不知道数据是否可靠，最终仍需人工支持才能接入”。最可能需要提前处理的是以下风险。

### 实质风险与行动计划

P0 表示扩大对外采集使用前应核实并满足的交付门槛；若实现已有相关能力，补齐证据和文档即可。P1 表示下一轮试用优先跟进；P2 表示结合使用反馈继续观察。这里不等同于已经确认存在代码缺陷。

负责人为建议职能，需由团队落实到具体人员；时间按下一次试用或发布节点安排，不虚构项目日期。

| 风险 | 优先级 | 处理动作与完成证据 | 建议负责人 | 完成节点 |
| --- | --- | --- | --- | --- |
| 新旧映射及统计含义被混用 | P0 | 完成映射与统计字典；用已知输入证明输出口径一致，界面与导出均可识别 | SDK 工程与硬件协议负责人 | 下一次对外采集试用前 |
| 采集失败却被视为完整成功 | P0 | 对照状态表核实现状；验证设备断连、网页关闭、写入失败与进程重启后的结果 | 数据服务负责人和测试 | 下一次对外采集试用前 |
| 保存帧数被误当成完整率 | P0 | 给出时间与质量指标定义，提供含异常的示例记录，明确无法判断的源端损失 | SDK 工程与数据使用方 | 下一次对外采集试用前 |
| 用户选错语言或接入路径 | P1 | 发布能力矩阵和三个任务入口，观察首次用户能否独立选对并完成 | 产品与文档负责人 | 下一轮首次接入测试前 |
| 升级后无法解释历史文件 | P1 | 补录制元数据和兼容规则；用历史样本验证导出及重建结果 | SDK 与发布负责人 | 下一次影响数据语义的版本发布前 |
| AI 问答引用过时用法 | P2 | 回答标明适用版本和文档出处，持续检查典型问题 | 文档与问答维护者 | 文档或 SDK 更新时 |

### 当前不应自动升级为阻塞项的顾虑

- **没有三维手模。** 对第一帧读取和可信采集不是必要条件；只有用户任务确实依赖空间展示时才提高优先级。
- **未发布公共 npm 或 PyPI 包。** ZIP 可以作为早期交付方式。先确保安装可复现、版本可查，再评估包管理分发是否解决主要障碍。
- **未做多设备同步。** 单设备采集成立时可以维持当前范围；客户需要双手或跨设备时间比较时，必须重新评估时钟与同步需求。
- **未做付费许可校验。** 是否需要取决于 SDK 是硬件配套工具还是独立收费产品，不能仅因缺少许可就判断产品不完整。

### 需要验证但尚无结论的关键假设

| 问题 | 验证方式 | 对优先级的影响 |
| --- | --- | --- |
| 主要用户是应用开发者还是实验采集人员 | 让现有客户展示最近一次真实任务、交付文件和卡点 | 决定主入口、Python、元数据和标注投入 |
| SDK 主要促进硬件使用，还是独立收费 | 对齐现有销售方式、交付责任和支持成本 | 决定许可、文档及售后策略 |
| Python 是否是主要工作流 | 核实实际使用语言、后处理方式及现有绕行方案 | 决定是否补齐产品级 Python 能力 |
| 回放和时间段标签是否阻碍当前交付 | 观察用户拿到 CSV 后的下一步，确认整段标签是否足够 | 决定先做离线重建、事件标记还是图形回放 |
| 跨机与多人访问是否真实存在 | 核实部署位置、操作者数量和控制权限要求 | 决定是否正式支持跨机模式及其安全要求 |

## 下一版本建议与成功指标

建议下一版本围绕“首次接入与可信采集”组织交付，先把现有能力变成用户可以独立完成的任务，再扩展新的展示和设备组合。

1. **核实目标任务与支持范围。** 用现有客户的真实任务确认主用户，明确哪些任务属于本版承诺。
2. **落实数据与采集约定。** 补映射、统计、归一化、时间、状态恢复、质量摘要及元数据，并保留可验证样本。
3. **同步完成接入交付与用户观察。** 补任务入口、能力矩阵、支持环境和发行包版本关系；首次用户观察可与数据规范工作并行开展。
4. **依据使用任务选择扩展。** Python、回放、分段标注、多设备和三维展示分别按证据排序。

建议先记录以下指标建立基线，数值目标在首轮观察后设定，不把未经测量的时限或成功率写成现状。

| 指标 | 计算或观察口径 |
| --- | --- |
| 首次成功取数时间 | 在支持硬件已就绪的前提下，从用户按文档开始安装到读取第一帧可解释的真实数据；保留未完成情况及失败原因 |
| 任务独立完成率 | 无人工代操作，完成指定任务并满足结果检查的人数占尝试人数；区分三个任务统计 |
| 录制完成率 | 正常完成且文件可校验的会话数，占正常完成、失败与中断会话数之和；真实与模拟分开统计。主动取消和仍在进行的会话另列，空记录单列并结合用户意图解释；该指标不代表源端数据完整率 |
| 数据解释完整性 | 抽查记录能否明确来源、单位、左右手、统计范围、版本和处理参数；按适用字段检查 |
| 支持负担 | 每次接入所需人工介入次数、耗时及首要原因，用于识别文档和接口问题 |

首轮可以邀请少量具有代表性的真实用户做任务观察，记录具体阻碍；小样本用于发现问题，不据此宣称整体成功率。

建议原结构文档在“当前能力边界”之后，按“产品定位与任务 → 接入选择 → 能力与环境矩阵 → 数据约定 → 采集故障行为 → 版本与验收”补充。这样每项技术能力都能对应到用户任务、可交付结果和验收依据。
