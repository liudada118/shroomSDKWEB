# Shroom SDK 产品评审与补充建议

评审对象：[Shroom 当前系统结构 1.1](C:/sdk/docs/obsidian/Shroom-当前系统结构-1.1.md)。日期：2026-10-19。

主用户已明确为购买 Shroom 设备、希望快速集成到自身应用中的客户。SDK 的产品目标是缩短客户从拿到设备到完成可用集成的过程，降低协议、映射、环境配置和异常处理带来的接入成本。

这份结构文档已覆盖用户任务、采集异常、数据含义、版本交付和成功指标。评审重点是让主入口、语言支持、示例与验收围绕客户集成展开，并为对外承诺补齐适用范围和通过证据。实验采集、新设备适配和界面展示按客户需要提供辅助路径。

以下评审针对文档表达和产品约定。文中所述当前能力沿用原文；建议方案不代表已实现接口。未核对源码或运行设备的事项，不认定为实现缺陷。

## 围绕客户快速集成的九项审查

### 购买设备后的集成过程需要贯穿交付

**已确认定位：**主用户是购买设备后希望快速集成的客户。客户内部实际使用 SDK 的人员按技术栈选择路线。

**反驳：**原文按组件和任务列出了能力，但客户还需要一条贯穿设备交付、下载选择、环境配置、最小例程和自有应用接入的明确路线。仅证明官方示例运行，仍不能证明客户已经完成集成。已支持设备的客户也不应在首次接入时承担协议拆帧和点位映射工作。

**补充决策：**产品定位写为“面向已购设备客户的快速集成 SDK”。交付指引从客户的已购型号和技术栈出发，给出兼容环境、对应发行包、最小例程及接入客户程序的方法。展示、采集、导出按需追加；新协议适配进入高级路径。

**验证办法：**让已购客户使用自己的设备和开发环境，完成例程运行、客户程序消费真实数据、字段解释、连接异常处理及资源释放。记录客户卡在哪一步，以及需要多少人工提示。

### 完整七步不能同时承担所有用户的快速开始

**原文依据：**“任务入口优先”“纯取数不强制录制与下载”；但快速文档要求“顶部突出完整 7 步”“1 先跑通完整示例”。

**反驳：**原则与页面顺序存在冲突。只想拿到第一帧的开发者，可能误以为必须先启动服务、打开网页和录制文件。“完整”不能自动代表“最快”。浏览器直连测试台还可能被理解成与正式集成等价的入口。

**补充决策：**文档第一屏以“快速集成已购设备”为主入口，按设备型号和客户技术栈进入最小例程，再说明如何接入自有应用。网页展示、录制导出、新设备适配放在辅助入口，七步完整示例归入展示与采集路径。每条路径明确最小依赖、终点和故障入口。

**验证办法：**给客户“在自己的程序中读取并使用设备数据”的任务，观察其是否能选对型号及技术栈并完成接入。纯取数集成不应要求启动网页或完成录制；需要服务的任务应在开始前说明原因。第一帧作为中间检查点，最终检查客户自己的程序。

### 列出待核实事项仍不足以形成支持承诺

**原文依据：**当前实现“沿用原结构快照”，范围包含未提交变更；环境、产品型号及固件组合仍待补。

**反驳：**读者能知道有不确定项，却仍不知道哪些组合可以放心使用。文档版本、SDK 版本和实际下载包不是同一个标识。只写 SDK 0.1.0，无法区分同版本下不同工作区或重新打出的 ZIP。

**补充决策：**对每个对外承诺，关联具体发行包标识或校验值、文档版本、环境组合和验收记录。没有证据的能力继续标为未验证。将“模块存在”和“该任务已验证通过”分开说明。

**验证办法：**另一位同事能够用被记录的发行包、文档、硬件和环境重现验收结果。对未提交工作区，可保存可识别的构建快照及配置；提交号不能单独代表未提交内容。

### 保留旧统计字段需要同时决定新的默认口径

**原文依据：**手套为 256 通道；每指主体 4×3，手掌 72 点，另有 pulp；兼容旧 195 点矩阵，“顶层统计仍按旧矩阵”。

**反驳：**文档已经提醒新旧统计不同，但提醒不能替代默认选择。开发者很可能直接使用顶层统计，并把它解释为全手统计。按已列出的五指主体和手掌计算，只能明确说明 5×12＋72＝132 个位置；这不是全部通道数量，也不能据此断定剩余通道是遗漏。pulp、保留通道、重复映射和旧矩阵之间仍需要完整对应关系。

**补充决策：**明确下一轮示例和界面默认使用的统计范围。每个统计附带参与点集合、有效点数、掩码和聚合方式；旧字段说明适用范围和替代方法。通道表应解释每个原始通道的用途，并区分展示位置数量和唯一原始通道数量。

**验证办法：**使用已知单通道样本检查分区和左右手映射；多点样本检查聚合。示例、界面和导出对同一统计项给出相同含义。旧字段若保留，须有可执行的迁移说明。

### 录制完成不等于这份数据足以完成用户任务

**原文依据：**一次会话一个标签，“人工标签不是动作识别”；保存帧数不代表源端完整率；文件验收主要检查格式、帧数和解释信息。

**反驳：**文件可能正常写完，但全部是准备动作、持续无新数据、传感器饱和，或选错了左右手。技术完成率无法单独反映用户是否得到可用结果。把回放、标注全部列为后续功能，也不能省略当前任务的有效性判断。

**补充决策：**分开表达“文件是否正常结束”和“数据是否满足本次任务”。首轮可以让用户通过明确说明和人工确认检查设备、左右手、有效采集区间和异常摘要，不必先建设完整标注平台。整段标签只解释为会话标签。

**验证办法：**让用户将文件交给另一位分析人员，在不询问开发者的情况下识别来源、时间、通道、处理方法、标签含义和已知异常。任务若要求动作分段，再验证事件标记或回放的必要性。

### 服务端持续录制必须配套可发现和可结束的任务状态

**原文依据：**网页关闭后继续录制，重连可查询状态；“重连后主动显示活动会话”“恢复停止入口”仍为规划，多网页控制待核实。

**反驳：**将录制放在服务端有价值，但用户可能在重开网页后不知道任务仍在运行，也可能重复开始。查询接口存在，不代表用户能够恢复控制。设备连接状态、数据更新状态和录制状态也不能用一个“已连接”替代。

**补充决策：**建议首轮限定每个服务实例只有一个活动录制，界面同时显示连接、数据更新和录制状态。进入页面时先查询当前记录，再展示开始或停止操作。已有录制时，重复开始应返回现有状态或明确拒绝，不能静默创建额外任务。多页面的控制规则须选定并公开。

**验证办法：**在录制中关掉网页、重新进入、点击重复开始、停止后再次停止。记录身份和最终结果应一致，用户能看见活动任务并将其结束。该方案属于本轮建议，是否已具备需按现有实现验证。

### 展示与录制并行的承诺需要工作负载边界

**原文依据：**“降低绘图帧率不减少录制帧”，但尚无设备数量、持续时间、输入速率和资源边界。

**反驳：**把绘图和录制分开，不能自动保证高负载下的数据保存。CPU、磁盘、队列仍可能影响采集。没有负载条件的“不减少”容易被理解成任意条件下都不会丢数据。

**补充决策：**在已验证的设备、帧率、单次时长和磁盘条件内描述承诺。说明积压、溢出和写入失败的观测及处理方式；超出能力时必须暴露异常。实时显示的新鲜度与录制的完整性分别验收。

**验证办法：**用同一可计数输入比较有无渲染时的保存结果，覆盖目标持续时长和慢写入情形。源序号不存在时，只证明主机可观测链路内的结果，不宣称已证明源端无丢帧。仅有主机接收时间时，也不能推导传感器到屏幕的完整延迟。

### 语言支持需要匹配客户实际使用的技术栈

**原文依据：**Python 仅有基础串口与矩阵能力，“Python 完整链路”留待验证；CSV 和 JSONL 字段定义尚待补充。

**反驳：**现有 Node.js 封装更完整，不能直接成为要求客户使用 Node.js 的产品理由。若已购客户使用 Python 直接接入设备，仅提供基础串口会把产品协议和点位映射重新交给客户，削弱快速集成的价值。同时，离线分析、实时订阅、直接接入硬件仍应分别判断，不能把所有语言能力混为一项投入。

**补充决策：**按已购客户的实际技术栈确定本轮支持范围。若本轮交付承诺支持 Python 直接接入，产品协议、点位映射、结构化数据和连接生命周期应进入必要能力；网页渲染、快速服务和录制功能另按任务决定。客户只需离线分析时，可以优先提供文件读取示例。这些是投入与验收规则，不据此宣称当前能力已经齐备。

**验证办法：**让客户在其实际项目和技术栈中完成接入，记录跨语言服务、手写协议、重做映射等绕行步骤。若需额外服务，应说明客户收益、依赖和维护方式，并验证该路线是否满足交付要求。

### 成功指标需要连接下一次产品决定

**原文依据：**已有首帧时间、任务完成率、录制完成率和支持负担，但“先建立实际基线，再确定时限与成功率目标”。

**反驳：**不随意承诺目标值是合理的，但若没有本轮观察对象、负责人、结束条件和处理规则，基线可能长期无法产生。技术任务完成也不足以回答 SDK 是否改善了硬件交付、应用集成或后续数据使用。

指标定义还有两处需要收紧。“无人工代操作”仍可能包含大量工程师提示，应区分无提示完成、提示后完成、代操作完成和未完成。已建会话的录制完成率，也不能覆盖创建记录之前的失败；原文已有任务完成率，必须把它与会话完成率同时观察，不能相互替代。

**补充决策：**以客户独立集成成功率、达到可用集成的时间和人工支持耗时为核心指标。第一帧时间作为中间指标，录制完成率只评价选择采集能力的客户。每个指标都关联一个决定，例如调整默认路径、修复高频失败点、缩小支持组合或投入客户所需语言能力。

**验证办法：**可以先观察 3—5 位具有目标任务的用户，以发现问题为目的，逐人记录结果。该数量是试用组织建议，不能据此推算总体成功率，也不能替代正式发布验收。

## 建议直接补入原文的产品约定

以下内容可作为“客户快速集成范围与验收”章节。主用户定位已确认，其余方案采纳后同步更新相应章节，避免在原有规划之外继续维护一套冲突的规则。

### 本轮主任务与取舍

- 主用户：购买 Shroom 设备、希望快速集成到自己应用中的客户。
- 产品定位：设备配套的快速集成 SDK，减少客户处理底层协议、点位映射和基础连接的工作。
- 核心任务：在客户实际技术栈中连接已购设备，将可解释的真实数据接入自己的程序，并能识别连接异常、正确释放资源及按约定恢复连接。
- 推荐主链路：确认设备型号与技术栈 → 检查兼容环境 → 获取对应 SDK → 运行最小例程 → 接入客户程序 → 验证数据与连接生命周期。
- 配套任务：按需要展示数据、录制数据、导出可独立解释的文件。
- 高级任务：新协议和新设备适配，单独提供诊断入口和完成标准。
- 暂不因本轮试用追加三维展示、多设备同步、完整标注平台或所有语言的 API 对等。
- 本轮语言范围：依据已购客户的实际项目确定。明确承诺支持的技术栈，须有对应产品级接入示例和验证证据。

### 用户任务与最小路径

| 用户目标 | 最小路径 | 成功结果 |
| --- | --- | --- |
| 将已购设备接入自己的程序 | 型号与技术栈 → 对应 SDK → 最小例程 → 客户程序消费数据 | 正确解释并使用真实数据，识别断连，按约定释放及恢复连接；当前各语言能力以原文为准 |
| 在网页展示数据 | 产品取数 → 快速服务 → 浏览器客户端 → 产品视图 | 看见数据更新，能区分断连、无新数据和正常显示 |
| 生成采集文件 | 产品取数 → 快速服务 → 录制控制 → 按记录 ID 导出 | 文件正常交付，来源、范围、参数和异常可解释 |
| 接入新设备 | 基础串口 → 协议拆帧 → 通道映射 → 样本验证 | 已知输入得到预期通道结果，并形成适配说明 |
| 接入既有主项目后端 | 已运行的主项目后端 → BackendSdkClient | 按该后端的协议完成查询或订阅；示例明确服务前提 |

主入口优先展示已购设备的集成路线，其余任务放在后续分支。浏览器直连测试台作为独立诊断入口说明其环境前提。最小示例需展示如何复制或引入到客户程序；完整七步示例用于展示与采集，录制与下载不成为基础集成的前置步骤。

### 支持承诺与证据

每个正式支持组合须记录以下信息：

- 发行包版本及可识别的包文件；同版本存在不同构建时，补充构建标识或校验值。
- 对应文档与示例版本。
- 操作系统、运行时或浏览器版本、连接方式。
- 产品型号、左右手，以及可获得的固件信息；无法获取的字段标为未知。
- 已通过的用户任务、测试条件、结果和问题记录。
- 最终责任人及验证时间。

支持状态按任务标注。基础串口通过，不代表录制导出通过；某平台有上位机下载，不代表该平台 SDK 路线已验证。当前文档未提供具体组合的通过记录，评审不替团队填入“已通过”。

### 数据语义与文件解释

- 指定推荐使用的产品分区及统计口径。旧 195 点顶层统计单独标明兼容用途，提供替代字段或明确的计算示例。
- 为 256 个原始通道建立可核对的用途说明，包含分区、位置、左右手规则、保留或未使用状态；一对多和多对一映射要能识别。
- 区分唯一原始通道数、显示位置数、有效统计点数，不能用其中一项代替另外两项。
- 每项统计说明输入范围、无效点处理和聚合方法。归一化值说明公式及参数，不能默认为跨设备或跨会话可直接比较。
- 为重建历史结果保留对应的映射文件、有效点掩码、处理顺序及参数。工件随记录或发行包离线提供，并以不可变标识或内容校验值关联；仅填写映射版本号不足以验证可复现性。
- 相对热力图的颜色需说明数值范围；若颜色尺度自适应，应让用户知道同色未必代表相同原始值。
- 时间字段明确设备产生时间或主机接收时间、单位和时钟含义。停止边界明确作用于哪一级已接收或已排队数据；没有设备时间时，不承诺精确截断设备实际采样时刻。
- 主机时间进一步明确接收、解析或保存时刻，区分用于日期展示的墙钟时间和用于时长计算的单调时间。说明同一帧在实时流、JSONL、CSV 中的对应方式。
- 导出文件附可对应的解释信息。可使用文件内元数据或同记录 ID 的配套说明，不强制某一种存储形式。
- “原始记录”明确到数据层级：串口字节、解码 ADC 或变换后产品数据。保留解码 ADC 不自动意味着可以重跑全部串口解析。
- 提供一份真实数据样例及其说明，覆盖正常记录；中断、空记录等样例按支持规则补充。

### 用户可见状态与数据质量

界面和诊断信息分别说明三类状态：设备或服务是否连接、最近是否有新数据、录制任务是否运行及落盘完成。已有连接不能掩盖数据停止更新。

建议首轮每个快速服务实例只允许一个活动录制。新页面进入时查询活动记录，显示记录 ID、标签、开始时间和可执行操作。网页关闭后继续录制的行为须在开始前可见，重开页面后提供恢复查看和停止的路径。

文件完成与数据质量分别记录。正常写完的文件仍可能包含数据中断、解析错误或用户无效操作；这些信息应保留。设备没有源序号时，源端完整性标为无法判定，不由保存帧数推导。

数据过期判定、设备断开后的处理、多页面控制和重复请求规则，在试用前选定并验证。阈值依据已支持设备的工作频率确定，不在缺少设备依据时统一写死。

### 发布门槛与问题处理

基础集成验收必须覆盖客户程序接入及连接生命周期。采集、导出和后台录制门槛适用于向客户交付相应能力的路线，不强制基础集成客户使用这些功能。

| 检查项 | 通过条件 | 影响范围 |
| --- | --- | --- |
| 路径可复现 | 在声明支持组合内，按发行包和对应文档独立完成该任务 | 未通过的路线不列为正式支持 |
| 客户程序接入 | 客户在实际技术栈中消费并解释真实数据，完成断连处理、资源释放及约定的恢复操作 | 基础集成能力的必要门槛 |
| 映射与统计 | 已知样本的通道、左右手、分区和统计与数据字典一致 | 影响相关产品数据使用 |
| 正常采集 | 起停及导出完成，文件与记录 ID 对应且能解释 | 影响采集能力交付 |
| 异常采集 | 断连、写入失败、服务中断等已约定情形有可解释结果，不被误报为正常成功 | 影响采集能力交付 |
| 恢复操作 | 网页重开后能发现活动任务，并按规则继续控制或结束 | 影响后台持续录制模式交付 |
| 工作负载 | 在声明设备、速率和时长内完成持续采集，异常和能力边界可观测 | 限定性能承诺范围 |
| 数据交付 | 另一位使用者凭文件及其说明正确读取和解释数据 | 影响对外实验数据交付 |

“待核实”进入验证任务。验证失败后，再根据影响决定修复、缩小支持范围或移出本轮承诺。对于发生在正式支持范围内、导致错误数据含义或错误成功状态的问题，应作为相关能力的发布阻断项。

每项门槛最终落实到一名具体责任人，并附结果和证据。SDK、协议工程、测试等职能名称用于协作分工，不能替代最终负责人。

### 试用指标与调整规则

| 观察结果 | 应触发的产品决定 |
| --- | --- |
| 用户选错路线或反复跨文档查找 | 调整任务入口、前提说明和最小示例 |
| 首帧主要卡在环境或设备配置 | 优先改善安装、端口选择和诊断提示 |
| 首帧成功，但数据解释或文件使用失败 | 优先完善数据字典、统计口径和示例文件 |
| 页面重开后无法判断录制是否继续 | 优先修复活动任务可见性和恢复控制 |
| 客户仅需用 Python 分析文件 | 优先验证文件读取示例是否满足任务 |
| 已购客户需用 Python 直接集成设备 | 将产品协议、映射和连接生命周期纳入该交付路线的必要能力 |
| 用户能运行示例，但无法进入自己的应用 | 改进最小集成示例和异常处理约定 |

任务观察须从预先定义的起点记录尝试，覆盖未创建记录 ID 的启动失败。尝试可通过本地观察表登记，并在产生会话后关联记录 ID，不要求先建设自动埋点系统。同一次任务内的超时重试和重复点击不能重复计为新用户；超时后实际创建成功的记录须核对，未决尝试另列并规定结算时间。

独立完成率仅计入无额外人工提示的完成者；提示后完成和代操作完成分别列出。首帧计时可以保留“硬件已就绪”的前提，同时单列硬件准备和环境阻塞，避免遗漏实际接入障碍。

客户独立集成成功率按已开始接入的目标客户统计：客户在承诺支持的环境与技术栈内，无额外人工提示地完成自有应用接入、数据解释及约定的连接生命周期验收，才计为独立集成成功。仅运行官方示例或收到第一帧，记录为中间进展。支持范围之外的需求另列，并用于后续支持范围决策。

达到可用集成的时间从客户开始 SDK 接入计至上述验收完成，区分总耗时、实际操作时间和等待支持时间。未完成者记录退出节点和原因，不只统计成功客户。

产品负责人组织已购客户的集成观察，记录设备型号、技术栈、任务结果、首帧与集成完成时间、人工提示、代操作、支持耗时和首要失败原因。观察结束后，调整默认路径、支持范围及下一轮投入；成功率目标在实际基线产生后设定。

SDK 的价值观察还应包含结果是否进入用户自己的应用或分析，以及硬件项目是否减少了集成支持成本。商业收费与许可模式单独决策，不在需求证据不足时提前建设许可系统。

## 原文的合并与维护方式

不必继续扩大结构树。建议将已有内容按以下用途收敛：

- 系统结构保留组件职责、数据流、入口和当前边界。
- 产品约定集中记录已确认的客户定位、本轮集成任务、支持范围、默认行为和验收条件；同步替换原文“主用户待验证”等已过时表述。
- 数据字典、错误码、接口及文件格式放在已有 SDK 文档事实源，对其他章节提供链接。
- 支持组合和验收结果跟随实际发行包维护；未验证内容继续保持明确状态。
- 候选需求依据真实任务排序，避免与本轮承诺混排。

这次最值得优先落实的五件事是：按已购设备与客户技术栈组织主入口，提供接入自有应用的最小例程，确定默认统计口径，完善连接异常及资源释放说明，为承诺支持的组合补齐客户集成验收证据。采集恢复和文件交付在客户选择这些能力时按对应门槛验证。
